# AI 时代算法工程师重点能力与技能培养指南

> 面向大模型应用、传统 ML 与 AI 基础设施方向的算法工程师能力地图，用于自我评估、团队培养与招聘参考。

---

## 一、为什么能力模型要变

算法工程师的角色正在从「离线训练 + 论文指标」扩展为「全链路智能交付者」：

| 维度 | 传统算法岗 | AI 时代算法岗 |
|------|------------|---------------|
| 交付物 | 模型文件、离线 AUC | 可上线的推理服务 + 可衡量的业务指标 |
| 技术栈 | CV/NLP/推荐 + TensorFlow/PyTorch | 叠加 LLM、RAG、Agent、推理引擎 |
| 成功标准 | 榜单、论文、验证集 SOTA | 线上效果、成本、延迟、稳定性、安全 |
| 协作界面 | 主要对接工程 | 深度对接 PM、数据、平台、安全、法务 |
| 迭代节奏 | 周/月级训练周期 | 小时级 Prompt/配置变更 + 持续 Eval |
| 竞争壁垒 | 模型结构创新 | 数据、评测、系统、领域知识、闭环飞轮 |

核心职责的重心：**从「把模型训好」到「把智能可靠地送进产品里」**。

## 三、重点能力详解

### 1. 机器学习与深度学习基础（地基，不能丢）

**目标**：在 LLM 热潮下仍具备扎实的统计学习与深度学习根基，能处理非「纯对话」类问题。

| 技能点 | 具体内容 | 培养方式 |
|--------|----------|----------|
| 数学基础 | 概率论、线性代数、优化（SGD、Adam、学习率策略） | 教材 + 推导关键公式 |
| 经典 ML | 回归、树模型、聚类、特征工程、偏差-方差 | Kaggle / 业务 tabular 任务 |
| 深度学习 | CNN、RNN/Transformer、损失函数、正则、过拟合 | PyTorch 从零实现小模块 |
| 训练技巧 | 数据增强、类别不平衡、迁移学习、多任务学习 | 复现经典论文实验 |
| 领域模型 | 推荐、搜索、广告、CV、语音、时序仍大量存在 | 选 1 个垂直方向深耕 |

**关键判断**：问题是否需要 LLM？小模型 + 规则 + 检索是否更优、更便宜、更可控？

---

### 2. 大模型（LLM）核心能力

**目标**：理解生成式大模型从训练到推理的全链路，能针对业务做选型与改造。

| 技能点 | 具体内容 |
|--------|----------|
| 架构理解 | Transformer、Decoder-only、MoE、长上下文、多模态架构 |
| 训练阶段 | 预训练 → SFT → 对齐（RLHF / DPO / ORPO 等） |
| 微调实践 | LoRA / QLoRA / 全参微调、数据格式、过拟合与灾难性遗忘 |
| Prompt 工程 | System/User 设计、Few-shot、CoT、结构化输出、JSON 约束 |
| 能力边界 | 幻觉、指令遵循失败、工具调用错误、多轮漂移 |
| 模型选型 | 开源 vs 闭源、尺寸、多语言、领域模型、许可证 |

**必备动手项**：至少完成一次 SFT 或 LoRA 微调 + 一次对齐或偏好数据实验。

---

### 3. RAG 与知识增强

**目标**：让模型「有据可依」，降低幻觉，接入企业私有知识。

| 技能点 | 具体内容 |
|--------|----------|
| 文档处理 | 解析、分块策略、元数据、去重、版本管理 |
| 检索 | Embedding 模型选型、向量库、混合检索（BM25 + 向量） |
| 排序 | Reranker、相关性阈值、召回率与精度权衡 |
| 生成融合 | Context 拼接、引用溯源、上下文超长截断策略 |
| 评测 | 检索 Hit@K、答案 groundedness、端到端 QA 集 |
| 进阶 | GraphRAG、多跳推理、结构化知识库、实时索引更新 |

**常见坑**：只调 Prompt 不调检索；分块过大导致噪声；无离线检索评测直接上线。

---

### 4. Agent 与工具调用

**目标**：构建能规划、执行、反思的多步智能体，而非单次问答。

| 技能点 | 具体内容 |
|--------|----------|
| 范式 | ReAct、Plan-and-Execute、多 Agent 协作、人机协同节点 |
| 工具设计 | API Schema、幂等、超时、错误回传、权限边界 |
| 记忆 | 短期上下文、长期向量记忆、会话状态机 |
| 规划 | 任务分解、子目标验收、失败重试与回退 |
| 安全 | 工具滥用、Prompt 注入、越权调用、沙箱执行 |
| 评测 | 任务完成率、步数、工具调用准确率、成本 |

**原则**：Agent 复杂度越高，评测与监控成本越高——先简单链路跑通，再叠能力。

---

### 5. 数据工程与数据飞轮（算法侧的「生产资料」）

**目标**：高质量数据决定上限；能设计采集、标注、清洗与反馈闭环。

| 技能点 | 具体内容 |
|--------|----------|
| 数据采集 | 日志挖掘、用户反馈、合成数据、主动学习 |
| 标注体系 | 指南编写、一致性（IAA）、质检、难例挖掘 |
| 数据清洗 | 去毒、去重、PII 脱敏、偏见检测 |
| 构造数据 | SFT 对话构造、偏好对、工具调用轨迹、蒸馏数据 |
| 版本管理 | 数据集版本、血缘、可复现采样 |
| 反馈闭环 | 线上 Bad Case → 标注 → 训练/微调 → 回归 |

**与 PM 的交界**：标注规范、Acceptance Criteria、Bad Case 优先级——算法工程师应主动参与定义。

---

### 6. 评测（Eval）与实验科学

**目标**：用可复现、可对比的方式证明「变好了」，而不是凭感觉调参。

| 技能点 | 具体内容 |
|--------|----------|
| 离线指标 | BLEU/ROUGE（参考有限）、BERTScore、任务专用指标 |
| LLM 评测 | 黄金集、分类维度 Rubric、LLM-as-Judge 及其偏差 |
| 人工评测 | 抽样设计、双盲、一致性校准 |
| 在线实验 | A/B、分桶、因果与混淆控制 |
| 回归门禁 | 模型/Prompt/数据变更前后对比，阻断劣化发布 |
| 红队 | 越狱、注入、有害输出、隐私泄露探测 |

**必备产出**：评测脚本、基准数据集、实验报告模板、发布 Checklist。

---

### 7. 推理、性能与成本优化

**目标**：模型不仅要准，还要快、便宜、稳定，能在 SLA 内扩缩容。

| 技能点 | 具体内容 |
|--------|----------|
| 推理框架 | vLLM、TensorRT-LLM、TGI、llama.cpp 等选型 |
| 优化手段 | 量化（INT8/INT4）、KV Cache、批处理、投机解码 |
| 模型压缩 | 蒸馏、剪枝、小模型替代路由 |
| 服务架构 | 多模型路由、缓存、异步、流式输出 |
| 资源管理 | GPU 利用率、并发、限流、降级策略 |
| 成本核算 | Token 单价、单次请求成本、缓存命中率 |

**关键指标**：P50/P99 延迟、QPS、单请求成本、GPU 显存占用。

---

### 8. MLOps / LLMOps 与工程化素养

**目标**：算法交付不是 Notebook，而是可版本化、可回滚、可监控的生产系统。

| 技能点 | 具体内容 |
|--------|----------|
| 代码能力 | Python 工程化、类型注解、单元测试、Code Review 习惯 |
| 流水线 | 训练流水线、自动化 Eval、模型/registry 管理 |
| 部署 | Docker、K8s 基础、CI/CD、灰度发布、Feature Flag |
| 可观测 | 日志、Tracing、质量/成本/延迟大盘、告警 |
| 版本 | 模型、Prompt、数据、配置四元组版本对齐 |
| 协作 | Git、文档、与后端/平台工程师的接口契约 |

**趋势**：只会写训练脚本不够；**能独立把推理服务跑上线** 的算法工程师更稀缺。

---

### 9. 安全、对齐与 Responsible AI

**目标**：默认安全，而非事后补课；理解对齐技术边界与产品策略边界。

| 技能点 | 具体内容 |
|--------|----------|
| 对齐技术 | SFT 安全数据、RLHF/DPO、拒绝策略、宪法 AI 思路 |
| 防护层 | 输入过滤、输出审核、敏感词、分类器护栏 |
| 攻击面 | Prompt 注入、间接注入、数据投毒、模型窃取 |
| 偏见与公平 | 评测子群、公平性指标、伤害性内容控制 |
| 合规 | 数据跨境、训练数据版权、日志留存与审计 |
|  incident | 事故分级、回滚、对外说明与技术复盘 |

---

### 10. 系统设计与架构思维

**目标**：在方案设计阶段就做对权衡，避免「模型很强但系统撑不住」。

| 技能点 | 具体内容 |
|--------|----------|
| 架构模式 | 单体 LLM、RAG、Agent、大小模型 cascade、规则混合 |
| 可靠性 | 超时、重试、熔断、降级到规则/小模型/人工 |
| 扩展性 | 水平扩展、队列削峰、多租户隔离 |
| 延迟预算 | 链路拆解：检索 + 重排 + 生成 + 后处理各多少 ms |
| 技术选型 | 何时自研 vs 开源 vs API；Technical Debt 记录 |

---

### 11. 业务理解、产品思维与沟通

**目标**：技术服务于业务结果；能与 PM、工程、运营同频对话。

| 技能点 | 具体内容 |
|--------|----------|
| 问题定义 | 把业务问题翻译成 ML 问题与可优化指标 |
| 优先级 | 效果、成本、风险、交付时间的 trade-off |
| 沟通表达 | 向非技术人员解释结论、不确定性、方案风险 |
| 文档 | 技术方案、实验报告、决策记录（ADR） |
| 影响力 | 推动数据标注、评测基建、跨团队标准 |

**高级信号**：能主动说「这个需求不该用大模型」并给出替代方案。

---

### 12. 研究素养与持续学习

**目标**：在快速迭代的技术栈中保持判断力，区分 hype 与实质进展。

| 技能点 | 具体内容 |
|--------|----------|
| 论文阅读 | 抓核心贡献、复现关键实验、批判性看待榜单 |
| 信息源 | arXiv、顶会、开源社区、模型发布与 benchmark |
| 复现能力 | 最小成本复现 SOTA 或工业界关键 trick |
| 技术判断 | 何时引入新框架/新模型，何时等待生态成熟 |
| 分享文化 | Tech Talk、内部 Wiki、Mentor 初级同学 |

## 四、按方向与阶段的侧重

### 4.1 常见方向能力侧重

| 方向 | 加强项 | 可相对弱化（依团队而定） |
|------|--------|--------------------------|
| LLM 应用 / 业务算法 | RAG、Agent、Eval、Prompt、产品协作 | 大规模分布式预训练 |
| 模型训练 / 基座 | 预训练、对齐、数据、分布式训练 | 复杂前端 Agent UI |
| 推理 / 性能 | 量化、 serving、成本、架构 | 繁琐标注流程管理 |
| CV / 多模态 | 视觉 Transformer、融合、端侧部署 | 纯文本 RAG |
| 推荐 / 搜索 / 广告 | 大规模稀疏、实时特征、因果推断 | 通用对话 Agent |
| AI 平台 / MLOps | 流水线、registry、监控、资源调度 | 单点模型调参 |

### 4.2 按职业阶段

| 阶段 | 重点投入 | 12 个月可验证成果 |
|------|----------|-------------------|
| 初级 | L1 基础 + L2 LLM 入门 + 编程规范 | 独立交付 RAG/微调模块 + 基础 Eval 脚本 |
| 中级 | L3 应用架构 + L4 推理与 MLOps | 主导一条 AI 功能链路，建立评测与回归体系 |
| 高级 | L4 系统优化 + L5 技术选型 | 设计团队级架构，成本/延迟/质量三角权衡落地 |
| 专家 / 负责人 | L5 方向规划 + 人才培养 + 壁垒 | 技术路线图、基建标准、关键难题攻关 |

## 五、推荐学习路径（可执行）

### 第 1–2 个月：夯实与上手
- [ ] 复习 ML/DL 基础，用 PyTorch 实现并训练一个小型 Transformer
- [ ] 完成 LLM API + RAG 最小 Demo（检索 + 生成）
- [ ] 阅读 1 份开源推理框架文档（如 vLLM）并跑通本地推理

### 第 3–4 个月：微调与评测
- [ ] 完成一次 LoRA SFT + 验证集对比实验
- [ ] 为负责场景构建 100+ 条黄金评测集与自动化脚本
- [ ] 参与一次线上 A/B 或灰度发布的技术分析

### 第 5–6 个月：系统化
- [ ] 设计带降级策略的推理服务方案（含监控指标）
- [ ] 建立 Bad Case → 数据 → 训练 → 回归 的闭环流程
- [ ] 输出团队级技术方案模板 / Eval 规范

### 持续
- 每季度跟进 2–3 篇与业务相关的高价值论文或开源 release
- 维护个人「实验笔记本」：假设、配置、结果、结论
- 定期做红队与安全评测，而非仅盯准确率

## 七、常见误区（避坑）

| 误区 | 正确认知 |
|------|----------|
| 「会调 ChatGPT API 就是算法工程师」 | 核心在数据、评测、系统与业务闭环，API 只是入口 |
| 「越大模型越好」 | 小模型 + RAG + 规则常是更优解；成本与延迟是硬约束 |
| 「离线指标高就能上线」 | 分布偏移、线上反馈、安全与成本常决定成败 |
| 「评测是 PM 的事」 | 算法工程师应主导 Eval 设计与自动化 |
| 「工程化是后端的事」 | 推理、监控、版本、降级必须算法深度参与 |
| 「追新论文就够了」 | 落地、维护、ROI 与团队基建同样决定职业高度 |
| 「忽视安全合规」 | 一次重大事故可能抵消半年模型优化 |

## 八、与产品经理、工程师的协作界面

| 协作对象 | 算法工程师主要交付 | 期望对方提供 |
|----------|-------------------|--------------|
| 产品经理 | 技术可行性、指标、成本、风险、方案选项 | 清晰场景、优先级、Acceptance Criteria |
| 后端 / 平台 | 推理接口、SLA、监控埋点、降级策略 | 稳定基础设施、发布流程 |
| 数据 / 标注 | 标注规范、质检规则、难例定义 | 稳定标注产能与工具 |
| 安全 / 合规 | 红队结果、护栏方案、审计日志 | 政策边界与评审节点 |

**共同语言**：评测集、发布门禁、线上核心指标、Bad Case 分级——与 PM 文档中的 Eval 体系应对齐。

## 九、总结：AI 时代算法工程师的一句话定位

> **AI 时代的算法工程师，是把概率性的模型能力，锻造成可度量、可运维、可信赖的产品智能的人**——  
> 既要有模型深度，也要有系统广度；既追求效果上限，也守住成本、延迟与安全底线。

培养顺序建议：**ML/DL 基础 → LLM 与微调 → RAG/Agent 应用 → Eval 与数据飞轮 → 推理与 MLOps → 安全与架构判断**，避免只会调用 API 或只会闷头训模型。
